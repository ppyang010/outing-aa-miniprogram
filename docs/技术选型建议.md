# 出游分账小程序技术选型建议

日期：2026-10-15｜当前阶段：阶段 B（技术方案推荐，待用户确认）

## 一、推荐结论

第一版优先采用：**微信原生小程序 + TypeScript + 微信云开发云函数 + 云数据库**。

目标是一个人也能持续维护的小型共享记账产品，而非一开始就搭完整互联网平台。基于已确认需求进行工程判断，本次不做新的联网检索、不承诺最新版本、具体套餐价格、平台资格或性能，依赖兼容性与账号能力需建项验证。

设计依据：[产品与技术设计](<出游分账小程序-desgin.md>)；执行入口：[开发任务清单](<出游分账小程序-task.md>)。

## 二、各层推荐

| 层次 | 推荐 | 取舍与用途 |
|---|---|---|
| 小程序端 | 微信原生 WXML、WXSS、TypeScript | 当前只做微信；直接处理分享、生命周期和授权，减少跨端适配层 |
| 组件 | 原生组件为主，按需引入 TDesign Miniprogram | 用于表单、弹窗和反馈；不同时装多个组件库，首次接入验证基础库兼容和包体 |
| 页面状态 | 页面局部状态与轻量共享状态 | 不先引入复杂全局状态库，账本真实状态以服务端为准 |
| 服务端 | 云开发云函数，TypeScript 编译为兼容目标运行时的 JavaScript | 以活动、支出、结算等领域组织，不因26个逻辑操作就拆26套部署 |
| 持久化 | 云开发文档数据库 | 小活动共享账本，云端集中校验；数据库细节封装到存储适配层 |
| 身份 | 服务端云调用上下文获取微信身份 | 不使用昵称或客户端提交的用户编号鉴权；首版不自建密码体系，也不额外引入 JWT |
| 计算核心 | 独立 TypeScript 纯函数模块 | 金额解析、余分、净额、简化匹配可脱离微信环境测试；服务端权威执行 |
| 数据更新 | 写入成功后刷新、进入页面刷新、手动下拉刷新 | 首版不用 WebSocket；他人更改可通过刷新获取，正式结算提交仍强制复核版本 |
| 自动化测试 | Vitest + fast-check | 前者测试业务分支，后者随机生成金额／成员验证守恒；云数据库一致性仍要真实测试环境验证 |
| 开发工具 | 微信开发者工具 + 编辑器 + Git | 开发者工具负责预览与真机调试，Git 管理版本；不自动创建远程仓库 |
| 工程管理 | pnpm 单仓库；必要时使用 workspace | 统一前后端语言和依赖锁定，共享模块需打包进部署产物，不依赖云端访问本地 workspace |
| 代码检查 | TypeScript 严格检查 + ESLint + Prettier | 在提交／构建时运行；具体版本由目标运行时与小程序模板验证后锁定 |
| 运维 | 云平台日志、资源告警和备份 | 配置预算上限与使用告警；日志不记录认证凭据、完整邀请访问凭据和账本正文 |

Node.js 使用云函数平台实际支持且仍受维护的运行时，并匹配 TypeScript 编译目标、SDK和测试工具。不在未核验平台支持前指定某个“最新版”。开发电脑版本与云端运行时要做兼容验证。

## 三、为什么适合当前项目

### 1. 原生小程序优先于跨端框架

当前确定的是微信小程序，没有 App、网页或其他平台的上线需求。原生方案少一层编译映射，排查分享、登录、页面生命周期和真机差异更直接。代价是将来需要增加其他端时，页面通常要重写；可复用的是业务核心与接口，而不是承诺界面零成本迁移。

- 如果你已经熟悉 Vue，或者明确计划近期同时做 H5／App，可重新比较 uni-app + Vue 3 + TypeScript。
- 如果你熟悉 React，且确有多端需求，可比较 Taro + React + TypeScript。
- 不能因为“以后也许多端”就默认增加当前复杂度；也不能保证跨端框架能消除每个平台的适配工作。

### 2. 云函数优先于自建长期运行服务

第一版接口和流量预期较小，可减少虚拟机、反向代理、进程管理、证书续期和服务器维护工作。代价是平台依赖、资源配额与冷启动，需要实际测量；云服务不是永久免费，也不会代替业务鉴权与备案。

### 3. TypeScript 前后端统一

金额字段、接口结构和状态枚举可共享，减少前后端把“元”和“分”、付款人和录入人混淆的风险。静态类型不校验真实网络输入，云函数仍必须执行运行时校验。

## 四、架构与一致性底线

```text
微信原生小程序
    ↓ wx.cloud.callFunction
云函数：身份验证 → 活动权限 → 状态／版本／幂等 → 业务操作
    ├── 独立计算核心：均摊、余额、全局简化
    └── 存储适配层 → 云数据库事务与快照
```

- 所有业务写入通过云函数，客户端默认无直接写权限；小程序不能自己决定某笔钱“已到账”。
- 同一活动的支出修改、正式结算、到账确认和重新开账都参与同一版本一致性协议，不只给结算函数加一个锁。
- 金额只存整数分，同时检查安全整数与产品限额。不用普通浮点小数连续相加算金额；首版的等额分摊无需为了复杂度而引入大数金额库。
- 已确认转账写不可变流水并设置唯一来源约束；重复点击和响应丢失重试不能重复记钱。
- 前端刷新与未来监听仅改善显示及时性，不能替代服务端事务、状态及版本检查。
- 逻辑操作名只是接口契约，不等于云函数部署单元。一开始采用少量领域入口，内部清晰拆模块，不做微服务。

### 云数据库方案的验证门禁

先用独立测试环境验证：同活动并发修改与锁账、重复确认到账、确认与重新开账竞争、最大拟定活动容量下的事务文档数、快照大小及执行时限。

建议上限仍为每活动20人、500笔支出，但这不是已测能力。若底层不能按设计原子完成，不允许把正式结算拆成无保护的多步写入；应先调整容量或设计版本化快照／持久化任务，重新验收一致性。若平台约束与成本明显不合适，再切换备选后端。

## 五、备选方案及切换条件

| 场景 | 备选 | 为什么不是默认首版 |
|---|---|---|
| 你已熟练掌握 Java，并有可维护的服务环境；或更重视关系约束与复杂后台 | 原生小程序 + Spring Boot + PostgreSQL 或 MySQL | 事务与关系查询更直接，但需要维护应用部署、域名、HTTPS、数据库与备份 |
| 希望继续统一 TypeScript，同时需要更可控的服务与关系数据库 | 原生小程序 + Node.js 服务（如 NestJS）+ PostgreSQL | 可迁移性和管理能力更强，但比云函数多一套部署与运维责任 |
| 确认近期多平台上线且有 Vue 经验 | uni-app + Vue 3 + TypeScript，后端按上面二选一 | 多端目标成立时才抵消跨端适配成本 |

如果你本身是熟练 Java 后端开发者且已有部署资源，推荐权重可以改变；不能只按新手单人项目假设否定你的既有能力。当前未提供个人技术背景，因此默认以“减少维护负担、尽快验证产品”排序。

## 六、首版不建议引入

- Redis、消息队列、微服务、Kubernetes：尚无已证明的必要场景。
- WebSocket 和强实时协作：共享账本先做到可刷新、写入不丢和结算不冲突。
- 大型后台管理系统：不以“管理员直接改数据库金额”作为纠错方式。
- 支付、OCR、图片上传和多币种：超出已确认范围，也增加费用和隐私处理。
- AI 大模型算账：结算是确定性算法，必须可复现、可测试，不能让模型推测金额。

```text
出游分账小程序/
├── README.md
├── docs/                 现有设计、任务与选型说明
├── .planning/            仅本地规划，已排除公开版本管理

├── cloudfunctions/       拟建：按领域组织的云函数
├── packages/
│   ├── contracts/        拟建：接口结构、错误和状态约定
│   └── ledger-core/      拟建：金额和结算纯计算模块
```

前后端共享代码需明确构建边界，小程序包不包含服务端 SDK、密钥或数据库管理代码。

## 八、建议确认顺序

1. 用户确认推荐路线；若有熟悉的 Vue、React、Java 或已有后端资源，先告诉我，再调整选型权重。
2. 核验个人主体类目、AppID、云开发开通和实际报价；不先开付费服务。
3. 在本项目目录初始化代码与 Git，锁定兼容版本；验证云事务与身份链路。
4. 完成“创建活动 → 两人加入 → 记一笔 → 查看共享账本”的最短闭环，再扩展正式结算和重开账。
5. 正式结算能力必须通过设计里的权限、幂等、守恒及并发验收，再进入体验／上线流程。

本次只推荐与记录，不代表用户已经同意采用，也未安装依赖、编写代码、开通资源或执行真实云环境测试。
