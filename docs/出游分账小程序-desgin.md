# 出游分账小程序设计文档

最后更新：2026-10-15｜版本：1.0｜当前阶段：阶段 B（计划产出）

## 文档说明

本文是第一版设计基线，不代表已经开发、上线或获得平台审核许可。用户已确认产品主方向；文中标为“建议”的技术与容量参数是后续实现基线，不是已验证的平台能力。

配套：[开发任务清单](<出游分账小程序-task.md>)。需求、字段、状态、权限或验收规则变更时，先更新本文，再同步任务清单。

## 一、阶段 A 结论沉淀

### 1. 已确认需求

| 项目 | 结论 |
|---|---|
| 平台方向 | 按微信小程序规划 |
| 注册主体 | 个人身份 |
| 协作方式 | 多人进入同一个活动，各自记录支出 |
| 分摊规则 | 默认当前全员均摊；每笔可取消未参与者 |
| 结算规则 | 基于个人净额进行全局抵消，生成简化转账方案 |
| 资金边界 | 不接支付、不代收代付；微信聊天等渠道自行转账 |
| 收付款记录 | 付款人标记已付，收款人手动确认到账；不宣称自动验资 |
| 编辑权限 | 成员只改删自己录入的支出；创建者管理活动与结算 |
| 结算锁账 | 正式结算后禁止变动支出；纠错需显式重新开账 |

### 2. 代码落点判断

- 当前为新建独立项目，不复用或修改无关业务项目。
- 全部公开资料和后续代码在当前仓库维护，文档放在 `docs/`；本地规划记录不进入公开版本管理。当前尚未编写业务代码。
- 技术路线建议：微信原生小程序 + TypeScript + 云开发云函数／文档数据库；原生组件优先，按需使用 TDesign Miniprogram，核心算法使用独立纯 TypeScript 模块，Vitest 与 fast-check 验证。详细取舍与备选见[技术选型建议](<技术选型建议.md>)。这是待用户确认的推荐，不代表已采用或已验证环境。
- 第一版通过页面进入刷新、写后刷新和手动刷新同步显示，不引入 WebSocket；正式结算仍在服务端复核版本和事务。云函数按少量领域入口部署，不按逻辑接口数量拆成大量部署单元。
- 建议模块：身份、活动及成员、支出、结算、到账确认、审计。
- 业务写入统一由服务端接口处理；客户端不能直接写成员身份、金额分配、结算单、到账记录。
- 金额校验、均摊与全局结算为独立纯计算模块；服务端权威计算，前端预览不能代替服务端验证。
- 微信云开发是技术建议；具体账号是否可开通、套餐费用、数据库事务与资源配额，必须在建项时验证。不可把云开发当成备案豁免。
- 本文接口名称和实体均为拟新增对象，不是已定位的现有代码。

### 3. 术语映射

| 用户术语 | 拟新增对象 | 说明 |
|---|---|---|
| 出去玩一次 | Activity | 一次活动，对应一个共享账本 |
| A、B、C | Membership | 活动成员，绑定服务端识别的用户，不用昵称作为身份 |
| 谁记的账 | Expense.createdBy | 决定编辑权限 |
| 谁付的钱 | Expense.payerMemberId | 决定垫付归属，可与记账人不同 |
| 谁参与消费 | Expense.shares | 保存该笔参与者及分摊结果 |
| 算出还差多少钱 | Balance | 已垫付、应承担、已确认转账、剩余净额 |
| 最终账单 | Settlement | 不可变版本快照与简化转账清单 |
| 已经转过的钱 | ConfirmedTransfer | 由收款方确认的人工到账流水，不能记成消费 |

### 4. 暂不处理

支付接入、自动扣款、银行账户、收款码上传、微信账单自动导入、票据图片与 OCR、多币种、比例或自定义金额分摊、退款和负数支出、部分金额到账、结算外临时转账录入、成员身份合并、活动转让、公开广场、广告与会员。

已确认到账的人工流水第一版不开放直接撤销；真实误确认或争议时保留记录并停止继续结算，先核实并单独设计纠正流程，不能靠删除数据“修平”账本。

## 二、功能与页面

### 1. 页面清单

| 页面 | 主要内容与操作 |
|---|---|
| 我的活动 | 进行中、结算中、已结清活动；创建活动 |
| 创建活动 | 活动名称，创建者自动成为第一个成员 |
| 邀请及加入 | 通过微信分享进入邀请页，确认加入；昵称由本人填写 |
| 活动详情 | 总支出、成员、支出列表、当前个人净额；记一笔与结算入口 |
| 记一笔／编辑 | 内容、金额、付款成员、分摊成员、消费日期、备注 |
| 支出详情 | 付款人、录入人、每人分摊、修改版本；按权限提供编辑／删除 |
| 成员管理 | 成员列表、邀请管理、移除符合条件的成员 |
| 核对及结算 | 每人垫付／承担／已确认转账／剩余净额，预览方案及锁账确认 |
| 我的结算 | 我该付谁、谁该付我、已标记付款及待确认到账 |
| 历史结算 | 当前与作废版本、到账记录、重新开账原因 |
| 隐私与帮助 | 数据处理说明、退出／删除申请指引、问题反馈方式 |

展示“应收”和“应付”时必须出现付款方向，不单独用正负数让用户猜。账单确认文案明确：这是记账结果，不是系统代收代付。

### 2. 主流程

创建活动 → 分享邀请 → B、C 主动加入 → 各自记账 → 全员查看并核对 → 创建者预览结算 → 正式结算并锁账 → 付款人自行转账后标记 → 收款人确认到账 → 全部结清。

分享链接不意味着加入者可以跨活动读数据。服务端先验证有效邀请，再创建活动成员关系；仅知道活动编号不能加入或读取。

## 三、成员与权限

| 操作 | 普通活动成员 | 创建者 | 非活动成员 |
|---|---|---|---|
| 查看活动、支出、结算 | 可以 | 可以 | 不可以；仅有效邀请的最小活动预览 |
| 新增支出 | 记账中可以 | 记账中可以 | 不可以 |
| 改删支出 | 仅自己录入、且记账中 | 同样仅自己录入 | 不可以 |
| 选择付款人 | 当前活动有效成员 | 同左 | 不可以 |
| 管理邀请／移除成员 | 不可以 | 可以，受下面约束限制 | 不可以 |
| 发起正式结算／重新开账 | 不可以 | 可以，受状态约束限制 | 不可以 |
| 标记已付款 | 仅转账单付款人 | 仅本人为付款人时 | 不可以 |
| 确认或拒绝到账声明 | 仅转账单收款人 | 仅本人为收款人时 | 不可以 |

创建者发现他人的账目有误，应联系录入人修改，不获得偷偷改他人金额的权限。纠错动作及重新开账原因要留痕。

- 默认全员只在新建支出时取当前成员作为初始勾选项；提交时保存明确成员名单与分摊金额。
- 后加入的人不会自动分摊过去费用。已有账目的参与者变更属于显式修改，须记账中并满足版本校验。
- 成员被任何未删除支出作为付款人、分摊者或录入人引用，或被结算／到账历史引用时，不允许删除／退出成员关系；避免人消失导致历史不可解释。
- 未被引用的普通成员可在记账中退出，创建者也可移除；创建者第一版不支持退出或转让。
- 结算中及已结清禁止加入、退出、移除成员；重新开账后才允许符合条件的成员变动。
- 无法联系录入人且必须改动其账目的场景，第一版不提供管理员越权改账；列为后续产品扩展。

## 四、金额与分摊算法

### 1. 输入及精度

- 仅人民币。客户端可输入两位小数的十进制文本，转换为整数分；服务端仅接受正整数 amountCent。
- 禁止负数、零、小数分、科学计数法金额和超过安全上限的整数。
- 建议单笔上限 100,000 元；首版每活动最多 20 人、500 笔有效支出。累计金额也校验安全整数范围。这些是主动限制，需通过后端容量测试再决定是否放宽。
- 每笔付款人为一个活动成员；分摊者至少一个且无重复，付款人可不参与该笔分摊。
- 同名成员允许存在，但界面需增加可区分标记；所有关联始终用 memberId。

### 2. 余分处理

给定金额 M 分、k 个参与者：q = floor(M/k)，r = M mod k。将参与者按不可变 memberId 固定排序，前 r 人分配 q+1 分，其余分配 q 分。

分摊结果与参与者一起存储，并带算法版本 equal-v1；历史账单不会因为成员排序或展示昵称变化重新分配余分。

例如 100 元均分三人，按固定顺序为 33.34、33.33、33.33 元。每笔 shares 合计必须等于 amountCent。固定顺序存在可解释的余分偏差，第一版优先保证稳定、透明，不提供随机重新分配。

### 3. 原始净额

对成员 i：

原始净额 B_i = 为消费垫付总额 P_i − 应承担总额 S_i。

正数为应收、负数为应付，所有成员 B_i 总和必须为零。消费和还款是两类数据，不能把转账重新算成一笔消费。

### 4. 已到账后的剩余净额

对已经被收款人确认的实际转账：

剩余净额 R_i = B_i + 已确认转出总额 O_i − 已确认转入总额 I_i。

只有确认到账的记录参与 O、I；付款人点击“已付款”本身不减少剩余净额。收款人确认代表人工对账，不是银行或微信支付接口验证。

### 5. 全局简化

1. 分别取 R_i > 0 的收款人、R_i < 0 的付款人；零净额不参与转账。
2. 每轮按剩余金额从大到小排序，同额按 memberId 稳定排序。
3. 取最大应付和最大应收者，生成 min(应付绝对值, 应收) 的转账。
4. 扣减剩余金额，重复到全部为零。
5. 服务端检查每人执行方案后净额为零、没有自转账及零金额转账。

本算法是确定性的净额匹配，活跃非零成员为 m 时最多产生 m−1 笔；不承诺所有场景数学意义的最少笔数。

## 五、活动、结算与到账状态

### 1. 活动状态

- ACCOUNTING：允许记账与符合规则的成员管理，可看动态预览。
- SETTLING：正式结算已生成，冻结支出和成员；只能处理当前结算的付款标记和到账确认。
- SETTLED：当前方案已全部确认且剩余净额全零。空方案也可在正式结算时直接进入此状态。

预览不是锁账。正式结算需携带预览对应的 bookVersion；如果任何影响计算的支出、成员或已确认到账发生变化，返回版本冲突，要求重新预览。

### 2. 转账单状态

UNPAID（未标记）→ DECLARED_PAID（付款人声明已付）→ CONFIRMED（收款人确认）。

- 付款人可在确认前撤回声明；收款人可拒绝声明并回到 UNPAID，均留痕。
- 单笔第一版只能全额确认，不支持部分到账。先真实转账，再点击声明。
- 确认操作原子写入唯一 ConfirmedTransfer，并更新当前转账单及活动状态；重复请求不能重复入账。
- 旧结算版本的转账单只读，不得补确认或作为继续转账依据。

### 3. 接口状态前置条件

- settlement.finalize 仅允许 ACCOUNTING。
- transfer.declarePaid 仅允许当前有效 SETTLING 方案中的 UNPAID 单。
- transfer.withdrawDeclaration、transfer.rejectDeclaration、transfer.confirmReceipt 仅允许当前有效 SETTLING 方案中的 DECLARED_PAID 单。
- activity.reopen 仅允许 SETTLING／SETTLED，且无待确认声明。
- 每次变更在同一原子操作中校验活动状态、当前结算指针及订单／活动版本。先命中成功幂等记录且参数一致的请求重放返回原结果，不因当前状态已变化重复入账或误报失败。

### 4. 重新开账与重算

创建者必须填写原因，页面对全员显示“旧方案作废，请勿继续按旧方案转账”。

- 存在 DECLARED_PAID、尚未确认或拒绝的转账时，拒绝重新开账。先由双方核对处理，避免已转款但未入账时生成重复催款。
- 允许从 SETTLING 或 SETTLED 重新开账。旧结算标记 SUPERSEDED，未执行转账单作废，活动回 ACCOUNTING。
- 所有已确认到账记录保留且继续计入剩余净额，不随方案作废删除。
- 开账、旧版本失效、当前方案指针更新及版本递增必须原子完成；与到账确认竞争时只能一个先成功，另一方重新读取状态。
- 用户按已作废方案误转账、未标记却实际转账、或误确认到账，属于无法从人工状态自动识别的争议场景；界面提醒停止继续付款并核对。第一版不假装自动纠正，需在上线帮助中明确限制。

## 六、数据结构（拟新增）

统一使用服务端时间；金额字段为整数分；可修改实体有 version，活动有 bookVersion。业务编号不使用可猜昵称。

| 实体 | 主要字段 | 约束 |
|---|---|---|
| User | id、服务端登录标识、displayName、createdAt | 不采集手机号、定位、通讯录；登录标识不公开给其他成员 |
| Activity | id、name、ownerUserId、status、bookVersion、currentSettlementId、updatedAt | 状态和版本由服务端控制 |
| Membership | id、activityId、userId、displayName、role、joinedAt | activityId+userId 唯一；成员身份不随昵称变化 |
| Invitation | id、activityId、访问凭证摘要、expiresAt、revokedAt | 仅创建者签发和撤销；可多人用、须有期限；不记录明文访问凭证到日志 |
| Expense | id、activityId、createdBy、payerMemberId、amountCent、shares[]、description、occurredOn、note、algorithmVersion、version、deletedAt | shares 保存 memberId+amountCent；软删除留审计 |
| Settlement | id、activityId、revision、bookVersion、status、memberSnapshot、expenseSnapshot、balanceSnapshot、algorithmVersion、createdBy、createdAt、reopenReason | 快照不可变；一个活动仅一个当前有效版本 |
| TransferOrder | id、activityId、settlementId、fromMemberId、toMemberId、amountCent、state、version | 当前方案生成，金额与双方不可改 |
| ConfirmedTransfer | id、activityId、sourceTransferOrderId、fromMemberId、toMemberId、amountCent、confirmedBy、confirmedAt | sourceTransferOrderId 唯一；不可直接删改 |
| AuditEvent | id、activityId、actorUserId、action、targetId、版本与必要变更摘要、createdAt | 不存身份密钥或不必要个人数据 |
| IdempotencyRecord | actorUserId、operation、requestId、payloadDigest、resultRef、createdAt | 唯一操作键；相同键不同参数拒绝；到账唯一约束长期保留 |

建议索引：成员的 activityId+userId、userId+joinedAt；支出的 activityId+deletedAt+createdAt；结算的 activityId+revision；转账单的 settlementId+state；到账的 sourceTransferOrderId 唯一与 activityId+confirmedAt；审计的 activityId+createdAt。底层不支持某种唯一约束时必须采用确定性文档编号与事务实现等价保证，不可只靠客户端查重。

云数据库方案暂不涉及关系型数据库 DDL/DML 脚本；仍需集合初始化、索引、访问规则、版本化数据迁移与独立测试样例。若改为关系型库，先更新本文和任务清单，再另行设计数据库变更。

| transfer.rejectDeclaration | transferOrderId、expectedVersion、reason、requestId | UNPAID；仅收款人且有待确认声明 |
| transfer.confirmReceipt | transferOrderId、expectedVersion、requestId | CONFIRMED、流水编号、活动状态；仅收款人 |
| activity.reopen | activityId、expectedVersion、reason、requestId | ACCOUNTING、新 bookVersion；仅创建者，无待确认声明 |
| audit.list | activityId、cursor | 活动必要操作记录；成员可读，隐藏敏感内部字段 |

统一错误语义：未登录、无权限、资源不存在、输入非法、邀请失效、人数／支出限额、状态锁定、版本冲突、成员被引用、存在待确认转账、幂等键参数冲突、需要人工核对、服务繁忙。未经授权时不能通过错误细节泄露其他活动是否存在。

## 八、并发、失败与安全

- 两人同时新增不同支出允许分别提交；各笔写入与活动版本变更原子执行。请求响应丢失时重试同一 requestId，返回原结果。
- 同一支出并发修改采用乐观锁；后一请求冲突后展示最新内容，不静默覆盖。
- 所有支出和成员写操作均要在提交时校验活动仍为 ACCOUNTING；不能只在页面加载时检查。
- 正式结算在一致性事务中读取所需数据、复核 bookVersion、写快照与转账单、切换状态。确认到账、重新开账同样共享活动级一致性控制。
- 每活动 20 人、500 笔是建议产品上限；实现前必须验证目标云环境能在对应文档数、大小与事务时限内完成快照。若无法满足，先更新方案为数据库快照或服务端持久化任务，不能分批写后提前宣告结算成功。
- 对邀请加入、预览及写操作做频控和长度校验；邀请建议 24 小时有效，创建者可撤销。有效期由服务端校验，过期后重新签发。
- 断网时不展示“已记账成功”；第一版不做离线写入队列，允许保留本地表单草稿，恢复后显式提交。
- 服务端密钥不进入小程序包；日志不含认证信息、完整邀请凭据、完整账本正文。
- 共享账单仅本活动成员可见，所有查询都做活动隔离；数据库客户端访问默认拒绝，必要读取也需严格规则。
- 邀请被转发可能让非预期人员申请加入，加入前提示共享范围，创建者可撤销邀请并移除尚无引用的错误加入者；不做公开可搜索活动。
- 定义备份、恢复与数据保留规则，提供隐私与删除申请入口。退出登录不等于退出活动或清除共享账单；共享历史删除需按合规与完整性要求单独办理，不直接级联删除他人的账目。

### 重算的关键算例

原始方案中 B→A 20 元已到账，C 尚未付；创建者重新开账并把自己录入的餐费从 300 改为 240 元：

- 新垫付：A 240、B 180、C 120；总额 540，每人承担 180。
- 新原始净额：A +60，B 0，C −60。
- 保留 B→A 已确认的 20 元后，剩余净额：A +40，B +20，C −60。
- 新方案：C→A 40、C→B 20。B 不会被重复要求再付 20，之前多付的部分也得到抵消。

最终：A=240−20−40=180；B=180+20−20=180；C=120+40+20=180。

### 算法验收不变量

每笔分摊和等于费用；所有净额和为零；执行方案后每人余额归零；无自转账、零金额、负金额；输入顺序改变不改变同版本结果；已确认到账只计一次。后续用随机数据与边界测试验证，不以几个示例代替全面测试。

## 十、上架准备与非功能要求

1. 先核对个人主体当前可选类目，确认此记账用途匹配；不能虚报金融或其他不符实际的类目。
2. 注册并获取 AppID，添加开发者，按当前后台要求准备主体认证、小程序备案、名称图标简介及服务内容声明。
3. 如采用自建后端，另核对 HTTPS、合法域名配置及适用的域名／接入备案要求；云开发也不能省略小程序自身合规检查。
4. 按实际数据处理配置隐私保护指引；涉及平台隐私接口时按规则获取用户同意。昵称与账单可涉及个人信息，不能因“不用手机号”就申报完全不处理个人信息。
5. 使用体验版让至少三台真实设备走完整协作流程，覆盖 iOS 与 Android；测试越权访问、断网与重复请求。
6. 完成算法、接口与状态测试、备份恢复演练、错误与性能基线，再提交代码审核。
7. 提审说明强调共享记账及人工结算、不提供支付；提供审核人员可复现的完整测试路径。
8. 审核通过后单独发布；首次上线复核隐私授权、分享加入与结算，监控云端异常和资源支出。

认证费用、备案时长、审核周期、云服务资费未核定，不作价格、时长或审核必过保证。性能目标需在选择云环境后测量冷启动与结算耗时，先记录实测再设上线门槛；一致性与金额正确性不能以性能为理由降级。

## 十一、实施顺序与回滚边界

1. 项目准备：核验个人主体类目与云开发开通条件，确认独立代码仓库位置；不修改当前无关项目。
2. P0 数据准备：集合、索引、权限、版本字段、迁移和独立测试样例；本方案无关系型 DDL/DML。
3. P1 接口契约：先定义每个操作的字段、状态、错误、鉴权与幂等，再实现业务。
4. P2 分模块实现：登录与活动 → 邀请成员 → 支出均摊 → 全局结算 → 到账确认与重开账 → 页面串联。
5. P3 测试验收：测试可伴随模块编写，但各模块必须通过对应验收后才能进入发布门禁。
6. 体验、合规、提审、发布及持续观察。注册提交、认证付费、开通付费资源、提审和发布等外部写操作均需届时单独确认。

回滚只回退代码版本、不删除确认到账记录；数据迁移应向后兼容。遇到结算一致性问题时，暂停新增正式结算及到账写入，保留账单只读与数据证据，不能重新生成不同方案让用户继续盲目付款。
